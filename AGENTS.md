# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Better Markdown Links is an Obsidian plugin that adds support for angle bracket links (`[Title](<path with space/note.md>)`) and manages relative links properly (prepending `./`), plus link conversion (per-file, per-folder, entire-vault, and automatic), a force-Markdown link style that overrides Obsidian's own `Use [[Wikilinks]]` setting (as a setting and as its own command triad), a forced link PATH style that overrides Obsidian's own `New link format` setting (as a setting, and as a force-relative command triad), demotion of embeds to plain links, resolution of wikilinks Obsidian cannot resolve (by alias, or by creating the missing note), and an extended `app.fileManager.generateMarkdownLink()` overload. Rename/delete handling was dropped in 5.0.0 and belongs to the `advanced-rename-and-delete-handler` plugin; this plugin only suggests that plugin and offers it the settings the old handler used. It is built on `obsidian-dev-utils` (a dev dependency providing the `PluginBase`, component, command-handler, and link utilities the plugin composes).

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/` (e.g. `eslint.config.mts` → `scripts/eslint-config.ts`).
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (imports the SCSS bundle and re-exports `Plugin` as the default export)
  - `plugin.ts` — `Plugin extends PluginBase`; `onloadImpl()` wires up all child components (settings, the Advanced Rename and Delete Handler suggestion, link conversion, the rename/delete settings migration, and command handlers)
  - `advanced-rename-and-delete-handler.ts` — the id and display name of the plugin that owns rename/delete handling since 5.0.0, written once and shared by the suggestion and the migration, plus `MigratableSettings`, the payload half of the handover contract (its envelope — `migrateSettings`, the proposer, the applied flag — comes from dev-utils' `settings-migration-api`, so both ends compile against one declaration)
  - the migration itself is the dev-utils `SettingsMigrationComponent`, constructed in `plugin.ts` under contract `^1`. This plugin supplies only the two closures: `getProposedSettings`, which offers the legacy rename setting **with the include/exclude paths that scoped it** — those paths are what the vault-wide handler needs to keep behaving the way this plugin did, and they are proposed rather than moved, since this plugin's own copies still scope link conversion — and `retireProposedSettings`, which retires the pending value through `editAndSave` (never `setProperty`, or the retirement is forgotten on the next reload) only once the user applies the migration
  - `better-markdown-links-component.ts` — `LayoutReadyComponent` that installs the patches and dispatches conversion by trigger: `handleModify` (vault `modify`), `handleSave` (editor save, via the save patch), and `handleNavigation` (link navigation). Gating lives on `PluginSettings` (`shouldConvertLinksOn*`). The `processFile` gate also triggers conversion when a note's only pending change is a `file://` normalization — it parses external links (`shouldParse{External,FrontmatterExternal,MultiValueFrontmatterExternal}Links`) and checks `parseLinkResult.isFileUrl`. That gate reads the note's own content and hands it to `parseMetadata`, deliberately NOT `getCacheSafe`: `getCacheSafe` flushes every dirty `MarkdownView` of the note before answering, and this gate runs on the automatic triggers, so the save trigger reaches it while `TextFileView.save()` is still in flight. Another plugin that rewrites the editor right after the save (issue #40: Linter's `Lint on save` inserting YAML attributes) then had its insert saved a second time one tick after it landed, which left Obsidian's properties section in the editor rendering the frontmatter from before the insert until the note was reopened — on disk and in the metadata cache it was all present, which is what made it look like the other plugin's bug. A gate that only decides whether there is anything to do must not write; the conversion itself still flushes, because a rewrite that did not would be clobbered by the editor's own next save. `src/foreign-editor-write-on-save.desktop.integration.test.ts` pins it, and fails on both save modes if the flush comes back. It also owns the `GenerateMarkdownLinkDefaultParamsComponent` registration that maps the settings onto every generated link — `removeUndefinedProperties`, so an absent `linkStyle` stands aside for another plugin's default rather than clobbering it with `undefined`
  - `link-converter.ts` — `LinkConverter` performing the actual link conversion in the current file, a file, a folder, or the entire vault; also normalizes `file://` links (via `updateFileUrlLinksInFile`) when `shouldNormalizeFileLinks` is enabled, so every conversion surface (commands + automatic triggers) picks it up. `shouldForceMarkdownLinkStyle` overrides `getLinkStyle()` with `LinkStyle.Markdown` for one run, which is what the `Convert links to Markdown` commands pass, and `shouldForceRelativeLinkPathStyle` does the same to `getLinkPathStyle()` with `LinkPathStyle.RelativePathToTheSource` for the `Convert link paths to relative` commands
  - `link-conversion-mode.ts` — `LinkConversionMode` enum (dependency-free so it can be imported as a value from node-based integration tests without loading `obsidian`)
  - `link-style-mode.ts` — `LinkStyleMode` enum (`Markdown` / `ObsidianSettingsDefault` / `PreserveExisting`), dependency-free for the same reason. `Wikilink` is deliberately not offered
  - `link-path-style-mode.ts` — `LinkPathStyleMode` enum, dependency-free for the same reason, mirroring all four of dev-utils' `LinkPathStyle` values (`AbsolutePathInVault` / `ObsidianSettingsDefault` / `RelativePathToTheSource` / `ShortestPathWhenPossible`). All four are offered, unlike `LinkStyleMode`'s omission of `Wikilink`: none of them contradicts what the plugin is for, and two of them are what make `shouldUseLeadingDotForRelativePaths` and `shouldUseLeadingSlashForAbsolutePaths` addressable at all. There is no `PreserveExisting`, because dev-utils' `LinkPathStyle` has none
  - `plugin-settings.ts` — `PluginSettings` model (angle brackets, leading dot/slash, `linkConversionMode`, `linkStyleMode`, include/exclude paths, `shouldNormalizeFileLinks` for `file://` link normalization, `shouldAppendFileNameWhenDemotingEmbeds`, `shouldResolveLinksViaAliases`, `shouldCreateMissingNotes`, plus the two rename-handover bookkeeping keys). Two link-style accessors, not one: `getLinkStyle()` for links being CONVERTED, and `getGeneratedLinkStyle()` for links being GENERATED — the latter returns `undefined` outside the `Markdown` mode, because saying `ObsidianSettingsDefault` out loud would beat the `originalLink` inference embed demotion depends on. `getLinkPathStyle()` / `getGeneratedLinkPathStyle()` split the same way but for a DIFFERENT reason: dev-utils has no `originalLink` inference for the path style, and the `undefined` is about the `Object.assign` merge of the default params, which a stated key would clobber. `buildLinkPathStyleParams(linkPathStyle)` is the third: it decides whether the leading dot and slash are stated or left to dev-utils' inference, and both the converter and the automatic-conversion probe go through it so they cannot disagree
  - `plugin-settings-component.ts` — settings persistence, legacy-settings converters, and validators
  - `plugin-settings-tab.ts` — settings UI tab (`PluginSettingsTabBase`)
  - `generate-markdown-link-extended-impl.ts` — `GenerateMarkdownLinkPatchComponent` patching `fileManager.generateMarkdownLink` and adding the `.extended(...)` method. Its types come from the root `api.d.ts` (below), imported as `'../api.d.ts'` rather than re-declared
  - `embed-demoter.ts` — `EmbedDemoter`, demoting embeds to plain links in a file, a folder, or the entire vault. Conversion of the link's FORM only; the path style and wikilink-vs-markdown style stay `LinkConverter`'s job, which is why `generateMarkdownLink` is passed `originalLink` and only `isEmbed: false`. An embed with an empty alias pointing at a NOTE gains the target's basename, because `[](<x.md>)` would render as nothing
  - `unresolved-link-resolver.ts` — `resolveUnresolvedLinksInFile`, run by `LinkConverter` BEFORE `updateLinksInFile`. Points a wikilink Obsidian cannot resolve at a real note, by looking its text up against every note's `aliases` frontmatter and basename, and optionally by creating the note (in `fileManager.getNewFileParent()`'s folder). **Gated on `shouldResolveUnresolvedLinks`, which only the explicit convert commands pass** — wiring it to the automatic paths would create a note on every auto-save. `src/demote-and-resolve.desktop.integration.test.ts` asserts that invariant against a real Obsidian.
    - **The lookup answers with EVERY note that carries the name, and only an unambiguous answer is written.** `findNotesByAlias` returns the complete candidate list; the caller resolves on exactly one, and on two or more leaves the wikilink untouched. That return is placed BEFORE the `createNote` branch on purpose: an ambiguous name is not a missing one, and creating a third note answering to it would be strictly worse than the arbitrary pick this replaced. Leaving the link alone really does preserve the unresolved marker rather than handing it to the converter to mangle — dev-utils' own `convertLink` returns `link.original` unchanged whenever `extractLinkFile` finds no target, which is what makes "do nothing" a real position rather than a deferral. Verified in `node_modules`, not assumed.
    - **The walk therefore no longer stops at its first hit**, because proving a name unambiguous means seeing the whole vault. That is a deliberate cost: the walk loses the early exit it had on a match, in exchange for both implementations answering the same question instead of two subtly different ones. Anyone who minds installs the index.
    - **The alias lookup has TWO implementations and picks between them at the call**, `findNotesByAlias`. `findNotesByAliasInVault` is the walk this plugin has always done — `O(vault)` per link, so a whole-vault convert is `O(links × vault)`. `findNotesByAliasInIndex` reads the answer out of the name index of [Advanced Metadata Cache](https://github.com/mnaoumov/obsidian-advanced-metadata-cache) (its `Names` module, off by default) in a map lookup. The `README` and `demo-vault/03 Convert links.md` tell users about it. `src/demote-and-resolve.desktop.integration.test.ts` proves it end to end against the REAL plugin: a nested describe downloads the pinned release (`ADVANCED_METADATA_CACHE_VERSION`, cached under the gitignored `dist/integration-test-plugins/`), installs it, switches the module on, records every `getPathsByNameSafe` call and asserts both the resolve and the ambiguous case went through it. Its `afterAll` removes the plugin again and asserts the graft is gone, because every other alias case in that suite must keep proving the walk. Moving the pin is a deliberate edit, made when this plugin wants to prove itself against a newer index. **The index is reached by duck-typing the graft on CORE's method** — `(app.metadataCache.getLinkSuggestions as Partial<GetPathsByNameWrapper>).getPathsByNameSafe`, which that plugin's `Names` module grafts on — exactly as dev-utils' own `getBacklinksForFileSafe` reads `.safe` off `getBacklinksForFile`. Not a declared dependency and not a registry handle: this plugin builds against `obsidian` alone, a user who has never heard of that plugin loses nothing, and the fast path appears the moment one installs it with no release here.
    - **The index's answer is FINAL, not a first attempt.** It knows every name in the vault, so an empty answer means the name is not there; falling back to the walk on a miss would pay the full cost on exactly the links that go on to `createNote`. Its paths are filtered to markdown, because the index walks `vault.getFiles()` filtered by `metadataCache.isSupportedFile` and is therefore wider than `getMarkdownFiles()`. **That narrowing now decides AMBIGUITY as well as resolution** — a name carried by one note and one canvas is one candidate, not two — and a path no file answers to is dropped for the same reason: the index can name a path the vault has since lost, and counting it would make a unique name look contested.
    - **`normalizeAlias` is a SECOND copy, deliberately, and only the walk uses it.** The index normalizes its own keys, so the fast path hands it the raw link text; Advanced Metadata Cache adopted these two rules (lowercase, collapse whitespace runs) verbatim from here. The two must agree or the same link resolves differently depending on whether that plugin is installed — and since the answer now decides ambiguity, a disagreement no longer merely picks a different note, it can turn a declined name into a resolved one. Deleting this copy needs the index to be the only path, which needs a mandatory dependency, which is wrong for a default-off opt-in feature
  - `shouldResolveLinksViaAliases` **defaults to off on a semantic ground, not a cost one** (settled 2026-09-20 while routing the lookup through the index). Cost was the suspected reason and it no longer applies with the index installed. **The ambiguity half of the reason has since been FIXED rather than merely disclosed** — a name several notes carry is now declined, not guessed at — so what is left holding the default off is the other half, on its own and unchanged: the lookup matches by BASENAME, and reaching it at all means Obsidian's own `getFirstLinkpathDest` already said no, so a basename hit here is one core refused, matched only through this plugin's laxer normalization. The settings description says so, which is what makes the default explicable rather than merely conservative. Do not re-add the "the first one in vault order wins" wording to any user-facing surface: it described the behavior this fix removed
  - `commands/` — sixteen `CommandHandler` subclasses: convert links, convert links to Markdown, convert link paths to relative, and demote embeds, each in selection, in file, in folder, and in entire vault. The convert-to-Markdown and convert-paths-to-relative triads are palette-only (they do not override `shouldAddToFileMenu` / `shouldAddToFolderMenu`, whose base defaults are `false`), because a second and third nearly identically named row beside their style-agnostic sibling would cost more than they explain
  - **selection is a fourth SCOPE, not a per-command feature** — each `*-in-selection-command-handler.ts` extends dev-utils' `EditorCommandHandler`, greys out on an empty selection (`editor.somethingSelected()`, so an empty selection never silently means "the whole note"), shows in the editor context menu, and hands its back-end an `offsetRange` taken from the editor cursors; everything else (resource lock, abort signal, excluded-path prompt, `shouldResolveUnresolvedLinks`) is inherited from the shared back-end untouched. `EmbedDemoter` passes the range to `editLinks`; `LinkConverter` passes it to all three of its passes — `resolveUnresolvedLinksInFile` (`editLinks`), `updateLinksInFile` and `updateFileUrlLinksInFile` — whose params declare `offsetRange` since dev-utils 106.0.0, which also pins that the wrappers forward it. **Never cast a range into a params type that does not declare it**: a wrapper that stops forwarding it silently widens a selection command to the whole note. A range skips every reference without a file position (frontmatter, canvas), so the selection commands never touch frontmatter links
  - **the range's ends are taken verbatim from the editor** — no off-by-one. Dev-utils tests `reference.position.end.offset <= endOffset`, and Obsidian's `position.end.offset` is exclusive, exactly like the editor's `to` cursor. The dirty-buffer hazard is dev-utils' and is already handled: `editLinks` → `applyFileChanges` → `process` → `readSafe` → `saveNote` flushes the view before reading, so offsets measured in the buffer still describe what lands on disk. `src/demote-and-resolve.desktop.integration.test.ts` pins that against a deliberately unsaved buffer whose prefix shifts every offset in the note
  - `patches/workspace-open-link-text-patch-component.ts` — `MonkeyAroundComponent` patching `Workspace.openLinkText` to convert links on navigation
  - `patches/text-file-view-save-patch-component.ts` — `MonkeyAroundComponent` patching `TextFileView.save` (fires on auto-save and Ctrl+S, never on external writes) to convert after the write
  - `patches/editor-save-file-command-patch-component.ts` — `MonkeyAroundComponent` patching the `editor:save-file` command's `checkCallback` to tag the active file so a Ctrl+S save is distinguishable from an auto-save
  - `styles/` — `main.scss` plus `scss.d.ts` ambient module declaration
- **`api.d.ts` — repo ROOT, not `src/`.** The hand-written, self-contained declaration of the extended `generateMarkdownLink` overload (`LinkPathStyle` / `LinkStyle` enums, the options interface, the `.extended(...)` wrapper type). Root and fixed-named because it is a **distributed artifact a consumer copies**, not compiled source: it imports from `obsidian` and nothing else, so taking it costs no dependency on this plugin. The impl and the two suites that read it import `'../api.d.ts'` — the statement-level `import type` with the explicit `.d.ts` extension, which is the one specifier `node16` resolution and the shared lint config both accept (`'../api'` is TS2834, the inline `{ type X }` form is TS2846, and `'../api.js'` names a file this repo does not contain). Nothing checks the self-containment: `skipLibCheck: true` silences errors *inside* a declaration file, so an unresolvable import there is invisible to the gate and has to be read off the import list by hand. **It is also where the surface is versioned**, and the README section repeats it: the plugin widens a core Obsidian call rather than publishing an API, so there is no contract, no handle and nothing to negotiate — a member's plugin version is the whole of what a consumer can pin against. Every member has been there since `3.0.0` and none has changed since; a member added later says so in its own JSDoc.
- **`main` field** points to `src/main.ts` (Obsidian plugin source entry; built artifact is `dist/build/main.js`, not published to npm).

## Testing notes

### The mobile screenshot capture suite

The mobile frames are captured by **two different routes**, and which route a frame takes is a decision about that frame rather than a style choice:

- **A frame whose subject is not a focused field captures the PAGE** (`captureObsidianScreenshot`), which is byte-reproducible: no status bar and no clock, so re-capturing an unchanged frame leaves no diff. A real phone shows no keyboard on such a screen either, so raising one would make the frame *less* true.
- **A frame whose subject IS a focused field captures the DEVICE** (`captureDeviceScreenshot`), with the soft keyboard raised first. A page capture cannot show a keyboard: it drives Appium in the WebView context, so it photographs the page, and the IME is a system window that is not part of the page. That left the command-palette frame as a search field over a large empty band, with the caption band — drawn across the bottom of the image — landing on the field and clipping the typed text. **The cost is that the switched frame is no longer byte-reproducible**, since the status-bar clock and the battery indicator are in it. Do not "fix" that churn by putting it back on the page capture, and do not switch the other frames over for consistency.
- **Raising the keyboard takes TWO things**, which is why both belong to `obsidian-integration-testing` rather than being copied in here. The AVD is built with a hardware keyboard attached, so Android suppresses the on-screen one entirely — `withSoftKeyboardEnabled` lifts that for the duration of a shot and restores the device exactly, including restoring a setting that had never been written, which takes a delete rather than a write. And a WebView will not ask for an IME on programmatic focus alone: `raiseSoftKeyboard` lands a real touch on the field and then proves geometrically that it lifted, because nothing in the page reports the keyboard — `innerHeight`, `visualViewport` and the modal container all keep their full height with it shown. A failure writes the device framebuffer and the device's own input-method state to `dist/screenshots/`, because a bare assertion failure here is unreadable.
- **A passing lift check is not the same as a good frame.** The check asks whether the FIELD moved clear of the bottom; it cannot tell you the keyboard covered the thing the shot is evidence for. So look at a switched frame, every time, rather than trusting the measurement alone.
- **The field it touches is read off the suite, not assumed.** The command palette renders `.prompt input`, which is not the `.prompt-input` a suggester renders.
